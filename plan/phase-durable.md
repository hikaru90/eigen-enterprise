# Phase: durable — the agent harness becomes durable (pi-durable)

**Owner directive (2026-10-19, session):** use PyDurable (`@earendil-works/pi-durable`, the pi monorepo's durable agent harness — owner calls it "PyDurable"); no Cloudflare; "go with SQLite for the moment … instead of using another service, everything should run on the VPS bare metal"; the priorities are durability, multiplayer, traceability, and team visibility; test it on the local Docker box (`scripts/local-server.sh` / `ee/e2e/box.sh`).

**What pi-durable actually is (correcting the name, not the intent):** a TypeScript, MIT-licensed, ESM-only **durable agent harness** (`@earendil-works/pi-durable@1.3.0`, Node ≥22.19, zero native modules — storage uses Node's built-in `node:sqlite`). Conversations, model turns, tool calls and host state are committed to storage **before anything is shown**; a crashed process reopens storage and resumes the pending turn from its checkpoint. Conversations expose watchable state (`viewState`/`watch`/`watchEvents`) — the multiplayer/traceability layer. It is an embedded library, not a server, and its non-Cloudflare storage story is exactly "one SQLite file on the VPS".

## Design decisions (D1–D10, on record — owner can veto)

- **D1 — Pin exact `1.3.0`** for `@earendil-works/pi-durable`, `@earendil-works/pi-ai`, `@earendil-works/chord` (upstream breaks without notice; 1.0→1.3 took 10 days, every release carried breaking changes). All pi-durable imports live behind ONE server module so a version bump is a contained diff. Bumping past 1.3.0 is a breaking upgrade (upstream SQLite schema v2 makes the data dir non-rollbackable).
- **D2 — Storage = one SQLite file on the machine.** `openNodeSqliteStorage(<dir>/agent.sqlite, { prefix: "pi_" })`. Dir resolution: `EE_AGENT_STATE_DIR` if set; else `${EE_STATE_DIR}/agent` when the substrate-injected `EE_STATE_DIR` is present (ee units.ts injects it into every workload; `StateDirectory` survives blue-green redeploys; the release tree is read-only); else **fail loud**. Documented in `.env.example`.
- **D3 — Single owner enforced by us.** pi-durable has no cross-process locking; two openers eventually corrupt each other via id-mint collisions. The host takes an exclusive lockfile (pid-stamped, bounded retry, then loud failure) before `Harness.open`. The harness is **lazy-opened on first dispatch** (the health gate stays DB-ping only) and **cached on `globalThis`** like `recapTickHost` — one harness per process lifetime, reused across HMR recompositions, never closed on recompose. No graceful-close handler: recovery-on-reopen IS the feature.
- **D4 — All model calls stay in the LLM gateway (guardrail).** The bridge to pi-ai is a **custom provider whose `stream` implementation calls `llmChatCompletion`** — no direct provider HTTP, BYOK resolution, rate limits, retries, `activity_call_log` and PostHog cost tracking all intact. The gateway gains an optional OpenAI `tools`/`tool_calls` passthrough (today it has none) — still the only door. Streaming stays where it is (non-streaming → one delta, same as today's fallback path).
- **D5 — Tools execute through the kernel registry.** At each dispatch the engine builds a pi-durable extension whose tools mirror the current `selectToolSurface` (activation ∩ roles ∩ scope, fail closed) and whose `execute` calls `EngineContext.executeTool` → `KernelRegistry.execute`. Permissions, approval gate, audit and vcs commits are inherited for free; pi-durable additionally persists tool intents/results durably.
- **D6 — `durable` is a LoopEngine, opt-in per agent, and the orchestrator switches to it.** Registered next to `builtin-json` and `pi`; `AgentConfig.loopEngine = 'durable'`. `builtin-json` stays compiled in as the rollback (a config flip, not a deletion). `JourneyAwareAgentRuntime` is engine-agnostic and keeps working. The durable engine does NOT write `kernel_agent_session_events` — pi-durable storage is the history source for agents on this engine (double-bookkeeping would fork history).
- **D7 — Postgres keeps the index, SQLite keeps the transcript.** Migration `0086_durable_conversations` (+ journal idx 86 + schema file): `durable_conversations` — company-level (kernel-side, no RLS like all kernel tables), maps conversation keys (e.g. chat session id) → pi-durable conversation id, `agent_id`, `llm_user_id` (billing attribution survives restarts), timestamps. Per-user secrets NEVER enter SQLite.
- **D8 — Team visibility = live event stream.** Authenticated SSE endpoint fanning `watchEvents` out (snapshot on connect, then one batch per commit), plus a company surface listing durable conversations and the live event feed of the active run — multiple browsers watching one run is the multiplayer slice. Kernel events stay metadata-only.
- **D9 — Chat UI persistence unchanged.** The endpoint keeps writing `chat_message` rows around dispatch. Known, recorded limitation: if the server dies mid-turn, pi-durable finishes the turn durably (the reply is committed, visible in the live surface, and part of the agent's context for future turns) but the chat **bubble mirror** of that turn is lost with the dead request — mirroring settled durable turns into `chat_message` is a listed follow-up, not silently ignored.
- **D10 — No new services, ever, for this.** No Cloudflare, no Redis, no extra daemon: SQLite + in-process harness under the existing systemd unit. Repo `engines` bumped `^22.13.0` → `^22.19.0` (node:sqlite requirement; box installer pins Node 22.23.3 ✓).

## Out of scope (follow-ups, in order)

1. Durable **background** tasks (subagents, software-factory M0 tickets surviving restarts) — pi-durable's task half via the existing tickers.
2. Mirror settled durable turns into `chat_message` (closes D9's gap).
3. Gateway streaming (real token deltas in chat + watchEvents).
4. Postgres storage adapter (upstream sanctioned path: `registerStorageConformance`), if/when one SQLite file feels wrong.
5. Compaction policy + usage surfacing (`pi.usage` doc) in the visibility UI.

## Proof

- Unit: provider adapter, engine dispatch through the registry (permissions/approvals inherited), storage dir fails loud, lockfile single-owner, **crash-resume** (kill mid-run, reopen, pending turn completes from checkpoint, faux provider).
- E2E (dev server + mock gateway extended for tool calls): chat runs on the `durable` engine; the visibility surface shows the run live; a second browser sees the same stream.
- **The box**: fresh `ee/e2e/box.sh` systemd box → real installer → owner signup → mock gateway as BYOK provider → chat → visibility surface → **`systemctl restart` mid-turn → the turn completes after reboot** and its committed events are watchable. State file at `/var/lib/ee-state/eigenenterprise/agent/`.
